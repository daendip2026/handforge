# Repository Instructions

## Audience and scope

- This file is the shared baseline for every contributor and coding agent working in this repository. Do not put contributor-specific preferences or local-only workflows here.
- Keep instructions factual and current. Do not document commands, directories, or workflows that do not yet exist in the repository.

## Layout and cross-stack boundary

- `tracker/` is the Python capture and inference side. `avatar/` is the Unity and .NET side. `proto/handtracking.proto` is the single source of truth for the wire contract between them.
- A change to `proto/handtracking.proto` reaches both sides. State the effect on each side before changing it, and do not treat one side's tests as evidence for the other.
- Generated protobuf bindings are never hand-edited. Regenerate the Python binding with `tracker/scripts/generate_proto.py`; the C# binding comes from `avatar/HandForge.Proto.Codegen`.
- The two bindings are tracked differently because Unity compiles `.cs` under `Assets/` directly, with no build step that runs codegen first, while the Python binding is regenerated by `tracker/scripts/generate_proto.py`. Keep `avatar/HandForge.Avatar/Assets/HandForge/Proto/Handtracking.cs` committed and `*_pb2.py` / `*_pb2.pyi` ignored by `tracker/.gitignore`.
- Ignore rules live next to what they govern: repo-global patterns in the top-level `.gitignore`, subproject patterns in that subproject's own file.

## Repository boundaries

- Documentation, build steps, and verification evidence must depend only on tracked files and explicitly documented external inputs.
- Do not commit machine-specific state, credentials, or session logs. When environment characteristics matter, document a sanitized and reproducible description instead.
- Preserve unrelated work already present in the worktree. Keep changes within the requested scope.

## Decisions

- Accepted decisions live in `docs/adr/`, in the namespace matching the decision's scope: `system/` when it crosses the tracker/avatar boundary, `tracker/` when it is contained in the Python side, `avatar/` when it is contained in the Unity and .NET side.
- An ADR records a decision and the alternatives it rejected, not the mechanism that implements it. If it cannot be stated as "We will …" with a quality it achieves and a downside it accepts, it is not an ADR.
- When a decision is reversed, mark both the superseding and the superseded ADR instead of deleting the record.
- Do not restate an ADR's content elsewhere. Link to it.

## Engineering quality

- Prefer simple, explicit designs with clear ownership, dependency direction, failure behavior, and maintenance paths.
- Before adding a file, template, dependency, or process, identify its current consumer and its verification path. If either is missing, do not add it.
- Do not create placeholders, duplicate sources of truth, or disposable artifacts that later need cleanup or deletion-history documents.
- Existing documents and templates are inputs to evaluate, not requirements to preserve unchanged. Replace one only when the result has a current use and improves correctness, clarity, or maintainability.
- Refactoring changes internal structure without changing observable behavior. Existing tests must pass unchanged before and after; do not edit a test to fit a refactoring.
- Preparatory refactoring is allowed and expected, but keep it in its own commit so the refactoring and the feature stay independently reversible.
- Do not extract an abstraction for a presumptive second consumer. Name the current consumers; if there is one, keep the concrete code.

## Evidence and verification

- Match evidence to the risk of the claim. Prefer current primary sources: official documentation, specifications, and original research.
- Distinguish sourced facts, inferences, and recommendations. Record material assumptions and comparison conditions.
- Do not generalize from a single measurement or example beyond the conditions it supports.
- A performance claim must name the measurement that produced it and the limits that measurement states.
- Run validation proportionate to the change. Report what changed, what was verified, and what remains unverified.

## Third-party material

- The root `LICENSE` does not cover third-party or generated material. Before tracking or publishing an external asset, model, or dependency, record in `THIRD-PARTY-NOTICES.md` its source, its license or terms with a date or version, and whether use, modification, and redistribution are permitted.
- Reproduce a component's full license notice in `THIRD-PARTY-NOTICES.md` when this repository distributes its bytes, because that is when the notice-retention clause binds this project. Reference the upstream notice instead when the consumer resolves the component themselves.
- Binaries belong in Git LFS through the `.gitattributes` filter, not committed directly. `.vrm` is filtered today.

## Collaboration and delivery

- Surface conflicting or ambiguous requirements before changing the affected area. Continue safe work that is independent of the conflict.
- Present material tradeoffs and reasoned disagreement instead of silently choosing a direction or agreeing without analysis.
- Keep commits and pull requests focused, reviewable, and independently reversible. Describe the reason and the verification evidence; do not mix unrelated cleanup.
- Do not infer authorization to stage, commit, push, open or merge a pull request, publish, or add dependencies.
- At handoff, report unresolved questions and whether work is local, committed, pushed, or published.
